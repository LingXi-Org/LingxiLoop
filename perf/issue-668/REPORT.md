# 案例库性能结果

同一浏览器、机器与时段，旧版 adf2570a 和候选分别以 5206 / 5205 启动 Vite。API 夹具均固定延迟 100ms；交替各 10 次，采用 nearest-rank 分位数。原始数据在 filter-paired.json / open-paired.json。

| 操作 | 旧 p50 / p75 / p95 (ms) | 新 p50 / p75 / p95 (ms) |
| --- | --- | --- |
| 分类切换到匹配网格绘制 | 367.2 / 381.3 / 386.1 | 28.7 / 38.0 / 44.3 |
| 刷新到列表可操作 | 1580.1 / 1623.2 / 2021.5 | 1318.7 / 1467.1 / 1858.4 |

分类 p75 降低 90.0%；每次列表请求 1 → 0，旧版每次卸载主推，新版 10/10 保持同一节点。首次打开 p75 降低 9.6%，仍主要受共享应用模块、Vite 开发加载与浏览器调度影响；没有达到首次打开减半，未扩张到无关聊天代码。

假设/实现：列表 API 本来已返回全部当前组织可阅读内容，分类与全文检索可直接复用这份数据。取消每次筛选的 200ms 延迟及网络读取，并保持已有组织、用户、视图变更清理与中止机制。首开直接请求，去掉固定 200ms 等待。

测量修正：初版基准会把旧网格闪现误判为完成；最终计时同时检查目标分类、预期匹配数量、加载状态，再等待两次 rAF。错误采样已排除。脚本只用于此固定夹具，不注入生产产品。

复现：基线和新版使用同一 scripts/fixtures/cases-benchmark.ts 与 cases.tsx，分别打开 /cases?benchmark，通过浏览器工具导入 scripts/fixtures/cases-filter-check.mjs 并执行 measureCaseFilters(before, after)。脚本断言每组 10 条、正确结果数、新版零筛选请求、主推节点持续保留及 p75 至少减半。

这些是缓存开发资源下的本机实验室结果，不是生产真实用户指标。资源采样中的字节数为 0（浏览器缓存），末段加载资源来自共享聊天/头像模块；不能据此推断生产下载成本。未取得已登录生产会话与 CrUX 数据，线上性能结论尚未验证。

发布沿用会话授权和仓库 CI deploy 流程；无数据库或配置改动。回退使用兼容主线提交通过标准部署入口，不变更持久数据。
