# Public run activity contract — issue #120

The pinned runtime is `@lyyzka/lingxios@3.3.6`. Its public `RunView` owns lifecycle,
fences, draft retractions and committed answer selection. Its public tool events
own tool identity and order. Provider reasoning, model diagnostics, system prompts,
and internal events are never a source of user-visible explanation.

The product adds an explicit `chat.report_progress` native tool for short public
explanations and plans. This is an authorized product tool registered through the
published ToolDefinition API, not a new runtime or an import of runtime internals.
It publishes a versioned, validated presentation value through the ordinary
durable tool receipt/event path. Repeated reports for one ID are incremental
snapshots of that public explanation. Model-private thinking remains disabled.
The runtime does not expose token deltas for these reports; never describe this
as streaming the provider's reasoning tokens.

Native part provider metadata contains only a stable presentation ID, kind and
label. Content, tool outcomes and approvals remain in native parts. A settled
runtime envelope is the authoritative final answer; a draft from the published
answer-preview channel retains that classification while it is streaming.
Unclassified historical content remains visible outside the disclosure.

Tool history precedes the final answer, in native event order. Explicit public
explanations appear at their event position. Pending or previously requested
approvals, interruptions, errors and incomplete tool results remain visible.
Unknown duration stays absent: mounting time and event receipt time are not
execution timing. Long histories may be revealed incrementally but are never
silently truncated to the most recent calls.

The existing native limits still apply (512 top-level parts, 50,000 structural
nodes and depth 32; upstream stream frames are bounded at 2 MB). The browser reveals 40 activity entries at a time;
it does not delete older entries. Server metadata reads join the full
tenant/run/agent/principal/session identity before exposing persisted details.
Migration 0036 stores only allowlisted public labels/inputs/results and actual
tool execution boundary timestamps. It does not store a second execution
status or raw arguments. Internal or unbound background work skips this
presentation table. Presentation writes use a separate connection and failures
cannot roll back or relabel an authorized business action.

Plans report `activeIndex` as the number of completed steps. A completed plan
must report the full step count. Field descriptions and validation diagnostics
explain this invariant to the real model; no adapter invents completion.

## Failure inventory written before implementation

- Internal reasoning/model diagnostics, private result bodies, raw arguments or
  outcome gaps cross the server boundary.
- Arbitrary tool results impersonate an explicitly published explanation.
- Duplicate, stale or replayed events replace newer results or reorder a call.
- A long history silently drops early calls; native serialization rejects it.
- A text part becomes an answer by position instead of runtime authority.
- Cancelled/failed/unknown calls appear successful, or approvals move into a
  collapsed region after resolution/reload.
- Explanation updates duplicate content or lose stable identity after replay.
- Final citations, OpenUI parts, attachments or subtask content are lost.
- Request/action authorization changes before a public report executes.
- Unsupported runtime timing or reasoning is fabricated.
- Public plans lose step identity or claim completion without an explicit report.
- A trusted tool duration is confused with queue time or generated by the model.

Coverage belongs to the existing native transport/projection tests and isolated
runtime integration, followed by official tester-army/e2e browser checks and real
provider execution. Component fixtures are not real-model acceptance evidence.
