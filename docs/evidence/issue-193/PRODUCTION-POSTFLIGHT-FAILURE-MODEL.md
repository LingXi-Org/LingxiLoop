# Read-only production postflight failure model

Recorded before implementing `scripts/verify-visualize-production.mjs`. This tool may call only the Komodo 2.3.3 public read operations `ListServers`, `ListStacks`, `ListStackServices`, and `GetStackActionState`, plus public GET `/api/meta`, `/api/health/dependencies`, `/readyz`, and the protected `/api/readyz` status diagnostic. Public `/readyz` is the readiness gate; the `/api/readyz` response never counts as readiness evidence. It never calls Execute/Write, runs container commands, changes a deployment, or touches the soak. Root remains the sole publisher.

| Failure | Required handling |
| --- | --- |
| Secrets leak from configuration, environment, logs, network errors or redirects | Use Sigillo-injected API key/secret only in in-memory headers to the fixed Komodo origin. Reject redirects. Do not request full configuration, logs or container inspection. Construct output using explicit fields and validated identifiers/enums; never serialize a raw response/error. |
| A load-balanced health response hides a stale A/B service | Independently require exactly one Web (`lingxiloop`) and one Worker (`worker`) service in each expected stack. Validate each container's running/healthy state and immutable 40-character image tag. Correlate stack/server identity and require the two hosting servers healthy. Public meta is an additional check, not proof of each replica's application metadata. |
| A mutable tag or missing digest is mistaken for an immutable deployment | Match the supplied exact SHA tag, require validated `sha256:` image identifiers and nonempty `image_digests` evidence from the documented service response. Record Docker image ID and Komodo-reported image digests separately; the script does not independently resolve a registry manifest or assert that these two digest fields represent the same kind of digest. Never invent an expected digest or equate a tag to a content digest. Require consistent corresponding digest fields across the four services. |
| Stack is actively changing or observed data comes from different deployments | Read action state before and after service inspection, require every documented action flag false, and compare repeated service/container/image observations. This bounded observation is not a transactional snapshot or future availability guarantee. |
| Missing fields, duplicated services, wrong server association or unexpected enum values | Fail closed with a fixed reason and retain only sanitized evidence. Never silently ignore a missing health check or treat `running` alone as `healthy`. |
| Komodo returns cached Docker status | Record observation time, origin, container IDs and the fact that ListStackServices is Komodo-observed status. Combine it with fresh public readiness/meta probes. No claim of direct per-replica HTTP probing or Docker-inspect freshness. |
| Public health changes shape, version or dependency status | Require product/commit and published runtime 3.5.3/schema 12/protocol fields from `/api/meta`; require exact known dependency booleans and HTTP success from `/api/health/dependencies` and the existing public gateway `/readyz`. Missing fields, non-JSON, timeout or failed readiness means verification fails, not a successful partial postflight. `/api/readyz` is separately recorded as a status-only protected-route diagnostic; its 401 does not prove readiness and is not substituted for the `/readyz` gate. |
| Endpoint returns an arbitrary error body or unbounded response | Bound response bytes/time, ignore response bodies on HTTP failure, and emit only fixed endpoint/operation codes and numeric HTTP statuses. Do not print strings from server error/config/log fields. |
| Evidence overwrites a prior report or a failed run looks successful | Require a new exclusive output path before networking; write `pending` first and a whitelisted passed/failed report at completion. Exit nonzero on failure. No automatic mutation/retry/recovery action. |
| API health is mistaken for schema/data or full product acceptance | Explicitly mark SQL schema-46, legacy 0033 and four new tables as a separate release-owner read-only SQL gate. This script does not verify their data or exercise authenticated user workflows. It does not rerun the already completed backup. |

The API shapes must come from the official `moghtech/komodo` tag `v2.3.3`, especially `client/core/rs/src/api/read/stack.rs` and the corresponding stack/container/image/server entity types. The installed `km-x86_64 --version` reports `komodo-cli 2.3.3`. Live validation is limited to the listed read operations and public GET endpoints, using `/workspace/.lingxi-production/bin/lingxi-prod run` with an absolute script path because the wrapper fixes its working directory to `/workspace/LingxiLoop`.

## Verified API references and field whitelist

- [Stack read requests](https://github.com/moghtech/komodo/blob/v2.3.3/client/core/rs/src/api/read/stack.rs): `ListStackServices` and `GetStackActionState` take `{stack: name}`. `ListStacks` takes an optional query and `limit: 0` for all list items.
- [Server list request](https://github.com/moghtech/komodo/blob/v2.3.3/client/core/rs/src/api/read/server.rs): `ListServers` uses the same query/unlimited-list convention.
- [Stack entities](https://github.com/moghtech/komodo/blob/v2.3.3/client/core/rs/src/entities/stack.rs): stack IDs, expected server binding, enum state, missing-compose booleans/count checks, eight boolean action flags; selected Web/Worker service state, image and image digests.
- [Container list item](https://github.com/moghtech/komodo/blob/v2.3.3/client/core/rs/src/entities/docker/container.rs): only validated container ID, image, image ID and enum state are retained; Docker status is converted to a fixed healthy/unhealthy/starting label, never copied verbatim. Missing health status fails closed.
- [ImageDigest representation](https://github.com/moghtech/komodo/blob/v2.3.3/client/core/rs/src/entities/mod.rs): serialized image/digest strings. The script validates the known server-image repository and `sha256:` shape, without making additional registry calls.
- [ListStackServices resolver](https://github.com/moghtech/komodo/blob/v2.3.3/bin/core/src/api/read/stack.rs): reads `stack_status_cache().curr.services`. Repeated observations are therefore explicitly described as cached Komodo observations.

The script keeps only the three expected server names and two app stacks. It never outputs the other stacks, server addresses/public keys/errors/stats, container configuration, labels, mounts, networks, ports, environment or health-check logs. Public output is limited to numeric HTTP status, product/version/SHA, known runtime fields and exact dependency booleans. Unknown/malformed values become null and fail their owning checks.

## Invocation and acceptance boundary

```sh
source /workspace/.lingxi-production/env.sh
lingxi-prod run node --use-env-proxy /workspace/worktrees/issue193/scripts/verify-visualize-production.mjs \
  --sha <expected-40-character-release-SHA> \
  --output /absolute/new-production-evidence.json
```

The script needs only injected `KOMODO_API_KEY`/`KOMODO_API_SECRET`; it does not depend on an optional webhook URL. It fixes both origins (`ops.christmas1314.xyz` and `loop.lingxilearn.cn`), takes two bounded inventory/health observations, and exits nonzero for missing, mismatched, changing or unhealthy evidence. Use a new output filename for every invocation. A successful baseline run against the old `b76c4cc` release validates this read-only tool and current old services; it does not accept or deploy the Visualize release. After deployment, Root must rerun with the final immutable SHA and independently complete the authorized SQL schema/data gate.

The first read-only baseline attempt, [production-readonly-baseline-b76c4cc.json](production-readonly-baseline-b76c4cc.json), is **failed**, not a postflight pass. At 2026-10-19 12:58 UTC both observations found all four containers running/healthy on `b76c4cc00f545ddbca27bced6628e1ed191e6777`, matching image identity, no stack action, correct public meta/runtime and healthy dependency diagnostics. Public `/api/readyz` returned HTTP 401 twice. Source inspection explains the difference: `workers/control-plane/src/index.ts` only publicly forwards `/api/health*` and `/api/meta`; gateway `/api/*` routes through that authenticated control plane. The existing gateway has a separate `location = /readyz` forwarding directly to the application readiness route. Root explicitly corrected the requested target to that existing public `/readyz` endpoint. The script retains `/api/readyz` as a protected status-only diagnostic and does not reinterpret its 401 as readiness success. The original failed report is retained; this correction changes no production configuration or control-plane code.

The corrected read-only baseline, [production-readonly-baseline-b76c4cc-readyz.json](production-readonly-baseline-b76c4cc-readyz.json), **passed** at 2026-10-19 13:02:22–13:02:46 UTC with no failed checks. Both observations found all four old-release containers healthy with matching immutable SHA/image identities and inactive stack actions. Public `/api/meta` and `/api/health/dependencies` passed; `/readyz` returned HTTP 200 with database, Redis and control dependencies true. `/api/readyz` returned HTTP 401 and is explicitly recorded with `countsAsReadiness: false`. This result verifies the tool against the existing `b76c4cc` release only; the final Visualize release still requires a fresh run with its exact SHA and Root's separate SQL verification.
