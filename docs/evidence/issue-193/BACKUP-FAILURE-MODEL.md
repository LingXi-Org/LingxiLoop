# Visualize backup rehearsal failure model

This document precedes implementation of `scripts/verify-visualize-backup.mjs`. The script is a preparation artifact; writing it does not prove that a production backup or migration rehearsal has run. Only the release owner may execute it with Sigillo-injected Komodo credentials. It must not stop services, deploy, migrate the live database, or touch the runtime 3.5.3 soak.

| Failure | Required containment / evidence |
| --- | --- |
| Online writes make dump and counts disagree | Hold one read-only repeatable-read transaction, export its snapshot, collect every native table in `public` and `lingxios` inside it, and pass the same snapshot to `pg_dump -Fc`. Release the transaction only after dump completion. |
| Snapshot owner exits, FIFO blocks, dump hangs, network drops | Private FIFO with an explicitly held writer; bounded process waits, connection/statement/idle timeouts and overall command timeout; trap closes the FIFO and terminates only the holder process. Never retry the mutating RunStackService request automatically. Report its update ID, or explicitly mark outcome uncertain if no ID was received. |
| Unexpected schema, modified historical migration, wrong runtime installation | Compare all 45 migration version/name/checksums with checked-out source, exact runtime 3.5.3/schema 12/protocol 11 and published schema resource hash. Validate the restored copy again before migration. |
| RLS, foreign tables, unexpected table names, or incomplete counting | Set `row_security=off`, enumerate all ordinary/partitioned tables in both namespaces with quoted identifiers; reject foreign tables. Counts include zero-row tables and `schema_migrations`; canonical JSON arrays support arbitrary identifiers. |
| Existing backup or database is overwritten | Require a concrete 40-character commit SHA, safe explicit attempt ID, and exclusive creation of the attempt directory. Generate a fresh isolated database name; record ownership only after successful `createdb`. Never reuse or drop a preexisting database. |
| Backup/restore fills the shared PostgreSQL volume | Before creating the backup directory, read `pg_database_size(current_database())` in a read-only transaction and `df` free bytes; require at least twice the database size plus 512 MiB. Recheck before creating the restore database for at least one database size plus 512 MiB. Reject at `capacity-initial` or `capacity-restore`; print only byte counts. This is a point-in-time guard, not a disk reservation or a guarantee against other writers consuming capacity later. |
| Restore errors or omitted tables | `pg_restore --exit-on-error`, exact pre-migration table/count equality and exact runtime/migration provenance comparison. Preserve the dump and its SHA-256 even if later verification fails. |
| Migration is accidentally applied to live | Migration SQL is only executed through the isolated-database helper, whose name is fixed at plan generation and checked against the live name. The live psql session is explicitly read-only. |
| Rollback leaves objects or a migration record | Execute the original 0046 bytes and migration record insert inside BEGIN/ROLLBACK; compare all original counts, runtime/migration provenance and a canonical catalog fingerprint, including relations, constraints, triggers, functions and types, before/after rollback. |
| Commit damages existing data or old OpenUI | Commit the original 0046 once in the isolated database; compare all old table counts except the expected +1 migration row, require exactly four new empty tables, preserve both 0033 tables, verify the exact version/name/checksum and unchanged runtime metadata. A second read-only provenance check is a no-op check, not a second DDL execution. |
| Credentials or row contents leak through output/errors | Read Komodo credentials only from injected environment. Read PostgreSQL password only from its service environment. Never interpolate credentials into commands, write them to files, print response bodies, or replay raw logs/errors. Emit only fixed status markers, IDs, versions, hashes, catalog counts and table counts. Dump files are necessarily sensitive backups, mode 0600 under a private directory. |
| Redirect forwards custom Komodo credential headers | Validate the exact HTTPS origin and either its root or listener path, reject URL credentials/query/fragment/ports, and use `fetch(..., { redirect: 'error' })` for both execute/read calls. The fixed API origin is sufficient; this rehearsal does not invoke a webhook. |
| Cleanup deletes a backup/live database, or cleanup fails silently | Trap drops only the exact successfully created isolated database, never the live name. Never remove backup directories. Remove only the script's unique temporary files. A cleanup error suppresses the success marker and leaves explicit failure evidence. |
| Lost response leaves an uncertain database/container operation | Poll only the returned Komodo GetUpdate ID. Timeout is uncertainty, not success or proof of cancellation. Do not rerun until the release owner inspects that update and attempt. SIGKILL/container death may bypass traps; database name and attempt are recorded before execution for manual reconciliation. |

Preparation checks are limited to JavaScript syntax, generated shell syntax and static inspection. Production success requires a completed Komodo update plus the verified report; none is implied by those preparation checks. A snapshot is not a write freeze: later production writes are not in this backup, and this script does not authorize or perform rollout.

## Application rollback is a separate problem

This rehearsal proves transaction rollback of the original 0046 SQL on a restored schema-45 copy. It does **not** prove that the old binary can run against committed schema 46, and does not implement any down migration or restore over production.

Read-only inspection of the pre-193 base `b2013edc` confirms both `server/src/bin/web.ts` and `server/src/bin/worker.ts` call `assertMigrationsCurrent()` before starting. `server/src/db/migrate.ts` validates applied migration versions/names/checksums against the old source list and requires the same migration count. Its old migration command also validates that list. Therefore merely skipping the old `db-migrate` service is insufficient: old web/worker startup also rejects an unknown applied 0046. After production commits 0046, use a reviewed fix-forward or a separately reviewed compatibility rollback build that intentionally understands schema 46. Do not delete the migration record, drop the new tables, or restore this snapshot over live data as an automatic rollback step.

## Release-owner invocation

Local plan generation needs no credentials and makes no network/database calls:

```sh
node scripts/verify-visualize-backup.mjs --plan --sha <concrete-40-hex-commit> --attempt <unique-safe-attempt> --output /tmp/visualize-backup-plan.json
```

After review, the sole release owner can use Sigillo to inject `KOMODO_API_KEY` and `KOMODO_API_SECRET` into the same command with `--execute` instead of `--plan`, and a different exclusive evidence output path. When `KOMODO_WEBHOOK_URL` is absent, the script uses the fixed production API origin `https://ops.christmas1314.xyz`; no webhook is invoked. Do not put credential values in arguments or files. Each invocation generates a new isolated database name. The exported `buildVisualizeBackupPlan()` and `verifyVisualizeBackup({ url, headers, plan })` functions also allow the owner to execute the exact in-memory reviewed plan. Before the remote call, the script uses read-only `git show` to verify that the concrete SHA contains all 46 exact migration checksums and the pinned 3.5.3 dependency.

Execution reserves the local evidence filename as `status: pending`; the file is only replaced with verified evidence after a successful completed update. A pending file, missing update ID, network timeout, or failed stage is not success and must not cause an automatic retry. A `createdb` response timeout can leave a new database without local ownership confirmation; inspect the recorded attempt/database/update before deciding how to clean it up. The durable backup always remains under `/var/lib/postgresql/data/visualize-upgrade-backups/<sha>/<attempt>`; `completion.json` is written only after the disposable database was removed successfully.
