# The driver owns answer and business-tool sequencing

The retained c5a265/b88c43 actual serialized requests contain both the trusted
driver's sequential-tool constraint and product instructions requiring a public
answer in the same response as a necessary native business-tool call. The
visualization host repeats the same-round assumption after skill activation.
An independent native public-answer tool cannot promise that pairing when
parallel tools are disabled. This change removes that product contradiction;
the driver remains the single owner of the wire format and legal turn shapes.

Failure boundaries, recorded before implementation:

- Initial, skill-selected and restored compiled requests must defer answer and
  business-tool sequencing to the trusted driver. They must not require the
  same response or an alongside-tools answer.
- Keep grounded useful explanation available before saving finishes. This
  permission is not a mandatory introduction, status-only preamble, self-review
  invitation or promise that an unsaved visualization already exists.
- Preserve private-content exclusion, truthful tool results, original source
  restrictions, actual delivery references, tool authorization and all existing
  schema, budget and qualification thresholds. Ordinary companion prose does
  not become a public answer.
- The confirmed public option `publicAnswerTool: 'native-v1'` is enabled only
  for the existing exact SiliconFlow DeepSeek profile with producer v3, alongside
  `publicTextContinuation: 'typed-message-v1'` and the existing sequential/native
  JSON capability settings. Other providers/models do not opt in; the shared
  public-text leaf and old protocol obligations remain unchanged. The OS owns
  private-v2 stripping and rejects the old native envelope combination.
- The old installed candidate and formal 3.8.10 do not expose the new option.
  No cast, private runtime patch or lock change makes them support it. The
  configuration-object check is independent of runtime behavior; final types
  and new-protocol checks require the exact next frozen development package.
- The next full serialized-request audit must use the real Worker/catalog and
  the frozen new driver. It must distinguish the one native public-answer tool
  from unchanged business schemas, observe initial/activated/correction/final
  requests, and preserve old failed evidence. These compiled product checks do
  not prove the new wire implementation or real-provider behavior.
