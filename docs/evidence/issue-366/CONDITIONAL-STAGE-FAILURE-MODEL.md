# Conditional explanation stage and host guidance

Written before implementation. This candidate is development only; it does not replace earlier failed real-provider receipts.

The optional native activation declaration quotes the current human request for explanation, authoring, supplied facts and optional language. Only the registered visualization workflow opts in. The runtime owns exact source binding, stage state and dispatch enforcement. Product guidance does not infer the stage from keywords, remove grants, certify semantic correctness or require a preamble for ordinary tasks.

Failure cases:

- A successful activation with the new declaration is rejected by the product's legacy three-key selector, so the next request loses its complete skill guidance. Unknown extra keys, malformed declarations, unsuccessful or stale-request steps must still fail selection; unchanged load/activation remains compatible.
- A stage accidentally includes reads/exports in its authoring set, or removes the selected skill or permissions while pending. Only save/chart/diagram/sliding_window are declared authoring actions. Native tests own pending/provided dispatch and provenance; product tests own exact metadata and selection.
- A different provider or private/internal response path lacks the stage's native sealing capability. The native activation gate must prove public v3, native public-answer tooling and typed continuation from the frozen runtime binding before accepting a declaration; unsupported paths must create no pending stage. Registration alone is not evidence of model capability. Undeclared activation and reference loading stay compatible.
- The registered skill still says the final response is the first visible text, or a later SKILL.md read reintroduces that restriction. The vendored file stays intact; an explicit, exact-match host projection is the registered and readable body, with its own version and content hash.
- Host overrides accumulate contradictory framing rules, require a same-round public/business call, force a progress preamble or force Chinese despite the user's language. The driver owns encoding; product rules cover task, audience, evidence and tools. Public progress preserves stable IDs and confirmed transitions.
- Prompt cleanup removes access boundaries, verified storage/current-version readback, numeric checks, truthful delivery, private reasoning boundaries or final-only group dispatch. These remain explicit and existing executable checks remain unchanged.
- An intermediate answer is incorrectly treated as verified task completion. Acceptance, citations, resource checks and complete-deliverable obligations still cover the whole answer; conditional stage state only records provision of its associated native answer.

Checks use actual ProductRuntimePolicy prompt compilation plus pure skill/reference calls. No network, database, real provider, budget changes, dependency-lock changes or production operations. New native workflow types require the forthcoming exact development package; the existing installed candidate is not represented as supporting them.
