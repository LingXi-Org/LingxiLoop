一次页面加载的六个阶段

从输入网址到看到网页

浏览器不是“一次请求”就把网页拿回来的。它先把网址翻译成服务器地址，建立一条连接，再用 HTTP 说“我要这个页面”，拿到内容后自己把文字、样式、图片装配成画面。前半程是在找路和建通道，后半程是在搬内容和排版，每一步都要等上一步的答案。

步骤
发生了什么

代价与常见故障
1
解析网址，先决定去问谁
拆出协议、主机名、端口、路径。有缓存就直接用，否则把主机名交给 DNS，并把该域名之前的连接、IP、HSTS 等记录翻出来复用。
浏览器
操作系统缓存
几乎零成本；故障是网址格式错或协议不支持。
2
DNS 把名字换成 IP
递归解析器依次问根、顶级域、权威服务器，拿到 A/AAAA 记录（IPv4/IPv6 地址），结果按 TTL 缓存。
本地/运营商递归解析器
根、TLD、权威服务器
未命中缓存时是首屏主要延迟；故障是域名不存在、解析超时、解析到错误地址。
3
建立连接：TCP 三次握手 + TLS 协商
TCP 确认双方都能收发；HTTPS 再做 TLS 握手，完成证书校验并协商出加密密钥。之后双方可复用这条连接发送多次请求。
浏览器 ⇄ 服务器
（含中间网络设备）
新连接至少要等一个往返；离得越远越慢。故障是连接被拒、超时、证书过期或不被信任。
4
发送 HTTP 请求，服务器处理后回应
请求带上方法、路径、头部（含 Cookie）。请求可能先到 CDN 或反向代理，再到应用服务器查询数据库；服务器回状态码、响应头和正文（通常是 HTML）。
浏览器 → CDN/代理 → 应用 → 数据库
等待时间取决于后端处理与距离；故障是 404、500、重定向循环、等待超时。
5
浏览器解析并渲染
边解析 HTML 边构建 DOM 树，解析样式构建 CSSOM，合成渲染树后计算布局、绘制图层并上屏；脚本与样式会阻塞解析，所以关键文件要优先到达。
浏览器渲染进程
（主线程 + GPU）
通常是首屏最大的一块成本；故障是脚本报错、样式未到导致画面闪烁、字体加载慢。
6
继续取子资源，页面逐步完整
解析中遇到图片、脚本、样式、字体会再发请求，共用已有连接、走缓存、按优先级排队；动态内容再通过脚本发起额外请求。
浏览器
CDN / 服务器
数量多、并发受限；故障是个别图片/字体加载失败，页面缺图或字体回退。
它们怎样配合：一条串行的链，之后才并行
前四步是严格串行的：不知道 IP 就没法连接，连接好的那一刻才是发请求的时刻。总等待量级可以粗略看成各段之和：
$$T_{\text{首屏}} \approx T_{\text{DNS}} + 2\,T_{\text{RTT}} + T_{\text{服务器}} + T_{\text{传输}} + T_{\text{渲染}}$$
其中 $T_{\text{RTT}}$ 是到服务器的一个往返时间（三次握手与 TLS 协商合计常要用到两个往返），$T_{\text{传输}}$ 约为 $\dfrac{\text{页面体积}}{\text{有效带宽}}$。所以“打开慢”要分段看：DNS 慢是解析问题，连接慢是距离或网络问题，后端慢是服务器问题，渲染慢是前端资源问题。
到了第 5、6 步，子资源才并行加载：CDN 把内容搬到离你近的地方，压缩与 HTTP/2、HTTP/3 的多路复用减少往返浪费，浏览器缓存让重复访问跳过前四步。
一个可以自己验证的观察方法
打开开发者工具的 Network 面板，勾选 Disable cache 后再刷新：在时间轴上依次看 DNS、Connecting、SSL、Waiting（服务器处理）与 Content Download 各占多长。清空缓存后重新访问，对比前后两次的区别，就能看到 DNS 与连接这两步被省掉了多少。
容易混淆的两个边界
DNS 只负责“名字到地址”，它不搬运网页内容；服务器返回的通常只是 HTML，样式、图片、字体要浏览器再依次索取。也就是说：页面“出来”的时刻，往往早于页面“完整”的时刻。
