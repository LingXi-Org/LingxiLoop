自建数据库 vs 托管数据库

判断标准不是“哪个更先进”，而是：引擎层的运维要不要自己扛、团队的稀缺资源是钱还是时间。下面四列给对照，右侧是判断该翻转的边界。

成本

看账单是不够的，要把人力与故障损失算进来。

自建
机器与存储便宜，但备份演练、监控值班、升级窗口都要自己出人。
托管
单价高，把引擎层人力打包进费用；团队小的时候通常更划算。
先算工时，再比价格

可靠性

托管保证的是机制，不是你的业务不出事。

自建
故障切换、备份恢复全靠自己设计与演练。
托管
高可用与备份看套餐；误删、慢查询、连接耗尽依旧归你。
无论哪种都留业务侧导出

运维责任

真正的分界线是“引擎层”归谁。

任务 自建 托管
安装、补丁、切换 你 厂商
表结构、索引、查询 你 你
连接、权限、配额 你 你
容量与扩缩容 你 大多厂商

适用边界

起步期产品形态还在变，托管通常是默认答案。

选自建，当…
有合规或数据驻留硬要求；必须用特定扩展/版本；规模极大且成本模型清晰；团队本就有数据库专精。
选托管，当…
增长不确定、无人值夜班、需要在几周内上线、没做过备份演练。

何时翻转判断

  1. 托管账单占云支出比例明显上升，且访问模式已稳定
  2. 出现法规、合同或客户明确的数据位置要求
  3. 必须用托管不提供的引擎能力
  4. 团队出现了真正的数据库工程能力

三个自检问题

明天数据库挂了，谁接手？上次验证恢复是什么时候？未来一年的数据量估算是多少？

有一个答不上，就先别自建。

年度成本对比

自建年成本 ≈ 机器与存储 + 人力工时 × 人力单价 + 故障与停机损失

托管年成本 ≈ 实例费用 + 附加服务费 + 少量运维工时

团队越小，“工时”那一项越可能压过差价。

推进方式

  1. 起步用托管，选满足高可用与备份的最小套餐
  2. 把数据库访问收敛到一个访问层，保留迁移余地
  3. 持续记录数据量、慢查询、账单构成、运维工时
  4. 等这些数字成为真正的痛点，再评估自建

讨论时怎么用

先把你们真实的数据量估算、预算和上线日期填进成本一列；再看“何时翻转判断”的四条是否被触发。四条都没触发，就别把时间花在自建上。
