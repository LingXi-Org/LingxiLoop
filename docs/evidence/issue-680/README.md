# Issue 680: staged shared-room membership

Ordinary groups now expose a Members action in the conversation header and list menu. A new group's binding records its creator. An active creator or an active course teacher already in the group can add active project humans and ordinary company agents, or remove another member. Existing groups without a trustworthy creator record require an in-group course teacher; no creator is guessed from array order. Teacher rooms, context-bound tasks and Slides editing rooms retain managed membership, with an explicit create-shared-group alternative. No private context is copied automatically.

Joining grants this group's existing shared history, subject to current company/project/conversation authorization. It grants no membership in any other conversation. Changes retain conversation/message/evidence identities. Conversation row, binding members, leader removal, monotonic membership version and audit event are committed together. Audit records identify actor, target, operation, project, version, resulting members, shared-history boundary and database timestamp. Repeating an effective add/remove does not create another audit or system message. Native agent additions use their authorized human principal. Existing policy/channel synchronization updates IM subscriptions and native orchestration; transient synchronization failure retains the committed binding for the existing reconciler.

Regression failure model was written before implementation in `conversations.test.ts`: creator denied; unintended private-history expansion; unavailable or foreign participant admitted; removed leader retained in orchestration; duplicate audit on retry. Tests exercise real HTTP/application/PostgreSQL boundaries and the native policy publisher. They use synthetic users and the established recording IM adapter; they do not prove real-model teaching quality or the original T16 user's production session.
