# Durable public activity: product failure model

Baseline: PR221 `121de820107c00a81e77f9583322ede8ca7d33ac`, published runtime 3.5.6. Written before product implementation. Upstream owns durable events, provider attempt identity, bounded publication and authoritative attempt endings; product consumes only its public API. Candidate packs are local checks, not formal release evidence.

1. An old failed/cancelled run falls outside recent 20 and has no assistant answer. A loaded IM source message or terminal run reference must discover it through product-owned bindings, including a bounded stable cursor when one page maps to more than 20 runs. Changing company/principal/conversation/project, internal/protocol identity, or revoking current membership must not disclose it. Anchors are lookup hints, never authorization.
2. Terminal/new-fence state arrives before seq-zero event replay; duplicate chunks, reconnects, preview resets, provider retry and revised requests must retain each published prefix exactly once with its recorded attempt identity. Commentary must not become the committed answer.
3. A public text delta is durable before the tool starts, survives tool failure/cancellation and reload, and occupies its original event order among tools. Public progress updates may update their original position only within their recorded request/attempt; old running entries cannot revive on retry.
4. More than 80 activity parts and 100 events retain latest commentary, current attention and final answer on the main snapshot, with all history reachable in 40-part pages. A changing attention filter must invalidate/reset its offset rather than skip records.
5. Product explicitly enables trusted publication with the provided bounded database/signal/deadline, checking current binding and frozen audience. Internal conversation, revoked participant, cross-tenant or candidate/reasoning/private values never reach public parts.
6. Loading an IM page must use that page's anchors; reconnect/reload and A→B→A scope changes must not apply obsolete recovery responses. One run is fetched once per recovery pass. No all-history scan, increased recent limit, new database schema or private runtime SQL.
7. Declared user text may still contain internal protocol/reasoning or repeated response-planning directives. Check cumulative text before durable publication: every split, including one character at a time, must withhold the ambiguous suffix. Preserve already approved prose; reject markers even after a normal introduction. Fenced/inline code and blockquotes are quoted data. An unfinished marker or inline-code delimiter cannot flush at EOF, cancellation or disconnection; accumulated planning directives cannot leak while waiting for a later rejection. UTF-16 approval boundaries cannot split a surrogate pair. The stream safety rule is separate from final citation/completeness validation. Runtime bounds may pause optional publication while allowing the model and fully validated final answer to continue.
8. A final provider hop may stream the same text later accepted as the answer. Its durable prefix must remain in history, but it must not become an extra foreground explanation above the identical answer. Only explicit runtime acceptance identity may relate these parts; do not infer identity by comparing strings or delete earlier tool explanations.

Owning checks: real local PostgreSQL + real product HTTP routes and public runtime APIs for history/authorization; real Worker with synthetic driver/provider for publication/stream/reload once the public candidate exists; existing official browser engine for actual chat component rendering. Record red/green and safe counts/identities only. Real provider, production rollout and long soak remain unverified.
