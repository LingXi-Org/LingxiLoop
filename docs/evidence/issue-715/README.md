# 技能加载失败修复

关联 #715。产品基线 `80c426bbbfbd506415984529ff10b606ef9d04fc`，正式依赖保持 `@lingxi-org/lingxios@4.0.0`，不引入新服务、依赖、数据结构或运行时适配器。

## 故障证据

仅对用户指定会话及项目的最近二十个运行做限定只读观察。输出只有技能身份、有限错误分类和布尔状态，不含聊天正文、提示词、凭据或原始工具输出；没有模型调用、重启、部署或写库。

[最终只读观察](https://github.com/LingXi-Org/LingxiLoop/actions/runs/42547712038) 确认一次 `skills.load` 的参数为 `name=skills__load`、`version=claude-design`，hash 与当前 Design 技能一致（前缀 `bb119ec92202`）。工具名被填进技能名，技能名被填进版本；SDK 按完整身份查找不能匹配，返回 `authorization_unavailable`、`executionState=rejected`。失败发生在准备阶段，动作账本没有该次回执，持久化步骤中保留失败；只统计账本会漏掉它。

实际 Worker 集成还复现了目录丢失：SDK 在工具目录裁剪后，为记忆投影浅复制上下文对象，原先以整个上下文为键的 WeakMap 无法命中；模型因此拿不到该步骤的精确注册目标。直接用原对象调用策略的单测没有覆盖这个行为。

## 最终实现

- 授权目录缓存以本次授权数组的身份为键，跨记忆上下文浅复制保留；主机重新授权生成新数组，不能命中旧目录。
- 技能加载与文档读取使用同一 `nextExplanationStep` 目标链，向模型提供当前授权注册项的精确 `name/version/hash`，并区分工具 `action` 与业务 `args`。移除原先单独的强制加载分支。
- 对第一次错误引用，只有原生回执明确拒绝、参数与当前引用不同、且权限仍有效时，才允许一次使用正确参数的新加载。相同参数失败、未知结果、审批、暂停、权限撤销和连续错误不触发强制重试。
- 不改写原调用或历史记录，不绕过 SDK 身份及权限校验；后续操作仍等待成功的原生加载回执。

## 回归与限制

正式 SDK 由现有 CI 的包读取身份下载，并按根锁文件的 SHA-1 SRI 校验一致后用于本地测试；未用相邻源码、重新打包产物或替身依赖。公开依赖位于临时目录，仓库依赖文件未修改。

`server/src/__tests__/first-action-contracts.test.ts` 在相同正式 SDK 下对照：基线十二项通过、三项失败；修复后十五项通过。随后加入 SDK 实际浅复制方式，先复现十四项通过、一项失败，再修复到十五项全部通过。覆盖精确加载目标、真实错位参数、一次纠正、同参数不重试、未知结果不重试，以及新授权快照不复用旧目录。

扩展现有 `runtime-first-action-contracts.test.ts`：实际 Worker、原生控制面及数据库，受控模型响应先发出生产中同形的错误引用，再从实际请求中的注册目标读取正确参数。验证原生拒绝、加载成功、指导注入、读取文档/页面、保存及检查。包含预期失败的场景明确记为合成恢复负例，不计为零失败交付资格。它不证明真实模型在所有请求中都能正确选择，也不代替生产会话重试。

最终精确候选的 owning server、相关数据库集成和独立只读审查结果见 PR。开发过程中已保留这些失败，未计作通过：

- 初始只读观察对 JSONB 步骤输出直接使用文本正则，查询失败；按 SDK 实际类型提取文本后重新观察成功。这属于诊断脚本缺陷，不是产品故障。
- 初轮新增测试的联合类型访问使 CI 类型检查失败，已修正；之后才取得上述真实行为失败→通过证据。
- 第一轮实现的真实 Worker 集成发现精确目标仍丢失，促成授权缓存浅复制修复。
- 本机全量类型检查受临时公开依赖版本影响，在未修改的两个集成断言上失败，不登记为通过；发布锁依赖的 CI 单独验证。

临时诊断和包获取只在独立 ops 分支执行，不进入修复 PR。尚未部署本修复，也未在生产中自动重放用户任务。
