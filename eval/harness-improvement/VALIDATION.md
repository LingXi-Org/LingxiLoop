# 验证与失败条件

1. 原 4.0.0 发布包、候选源码包、DeepSeek Harness 同期交替运行，不以历史延迟直接推断修复收益。
2. 保持原模型、任务文本、工具 schema、资源授权、精确评分、90 秒预算及每任务三次重复。36 个三元组按六种顺序均衡分配，共 108 个样本。
3. 候选只修改通用执行提示词，不识别 benchmark task ID，不硬编码答案，不注入 oracle，不更改授权。
4. 区分工具授权与必要性；回执或后台 verifier 不替代用户要求的显式读回。
5. 精简时保留权限、修订优先级、非可信内容边界、未知执行去重、取消/审批、部分完成和输出约束。
6. 诊断只采集时间、计数、hash、长度、状态和用量，不保存系统提示词、密钥或生产配置。
7. 记录请求首字节、结束、下游断开、重复请求指纹和消息字节数。上游观测耗时不是服务端纯推理时间。
8. 先完成 108 次受控模型 E2E，再跑同一协议真实模型；失败和缺失用量保留，不挑选替换。
9. 不修改生产依赖、数据库或部署；候选标为未发布源码补丁，不冒称正式包。

提示词策略属于语义约束，不是自然语言条件的确定性权限解析。保持运行时授权和持久化校验不变，由真实模型 E2E 判断改进。

第二候选：首轮只有提示词修改，27/36，不接受。先新增请求呈现/信任边界检查并确认旧实现失败，再将 trust=request 渲染为带 source/version 的原文 user 消息；其他信任等级继续保持数据封装。加强缺少能力时不探测资源的通用规则。所有首轮证据与源码快照保留在 results/round-1。
