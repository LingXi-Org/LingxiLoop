# 验证与失败条件

1. 原 4.0.0 发布包、候选源码包、DeepSeek Harness 同期交替运行，不以历史延迟直接推断修复收益。
2. 保持原模型、任务文本、工具 schema、资源授权、精确评分、90 秒预算及每任务三次重复。36 个三元组按六种顺序均衡分配，共 108 个样本。
3. 候选只修改通用执行提示词、授权说明及请求呈现，不识别 benchmark task ID，不硬编码答案，不注入 oracle，不更改授权。
4. 区分工具授权与必要性；回执或后台 verifier 不替代用户要求的显式读回。
5. 精简时保留权限、修订优先级、非可信内容边界、未知执行去重、取消/审批、部分完成和输出约束。
6. 诊断只采集时间、计数、hash、长度、状态和用量，不保存系统提示词、密钥或生产配置。
7. 记录请求首字节、结束、下游断开、重复请求指纹和消息字节数。上游观测耗时不是服务端纯推理时间。
8. 先完成 108 次受控模型 E2E，再跑同一协议真实模型；失败和缺失用量保留，不挑选替换。
9. 不修改生产依赖、数据库或部署；候选标为未发布源码补丁，不冒称正式包。

提示词策略属于语义约束，不是自然语言条件的确定性权限解析。保持运行时授权和持久化校验不变，由真实模型 E2E 判断改进。

第二候选：首轮只有提示词修改，27/36，不接受。先新增请求呈现/信任边界检查并确认旧实现失败，再将 trust=request 渲染为带 source/version 的原文 user 消息；其他信任等级继续保持数据封装。加强缺少能力时不探测资源的通用规则。所有首轮证据与源码快照保留在 results/round-1。

第三候选：第二轮仍为 27/36，拒绝接受。进一步精简通用规则，并在 runtime:authorization 说明当前目录是完整授权集合，先判断条件再行动；没有修改授权集合本身。第二轮全部证据与源码保留在 results/round-2。

第四候选：第三轮 31/36，成本下降但仍有 5 次多余读取，不接受为完整修复。在授权说明中按真实工具 effect 推导各 namespace 的只读状态；只读不等于禁止用户明确要求的读取，不能因其他 namespace 可写而扩大授权。三轮历史全部保留。

第五候选：第四轮 35/36，9/9 禁读任务与9/9 写后核对正确，但一次冲突恢复调用了网关未开放的内部辅助方法并被拒绝。将授权说明明确为上界，实际只能调用当前 provider schema 中存在的函数；避免把内部 grants 误当成可调用目录。保留第四轮全部证据；评分和网关仍完全不变。

适配器修正前明确失败条件：fixture conflict 必须在两边保留可辨识的版本冲突语义；不能统一变成未知失败。denied 和 invalid 同样保留授权/输入类别；任何失败不得变成成功，实际状态与原始工具尝试仍由同一 fixture 评分。替身 E2E 在冲突后的模型请求中检查版本冲突诊断，同时覆盖旧发布包与候选。前五轮的错误映射缺陷单独披露，不能用它们归因生产 runtime 的冲突处理质量。

第七轮：保留第六轮正确的错误映射；去除提示词中与 provider schema 重复的 grants 方法清单，只给出基于真实 effect 的只读状态。内部授权、capabilities 和缓存 fingerprint 仍保留；不是撤销/扩大工具授权。模型只从当前 schema 选择函数。第六轮 34/36 的两类失败完整保留。
